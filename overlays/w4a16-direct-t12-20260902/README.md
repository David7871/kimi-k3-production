# W4A16 direct SQG-XOR-Cheb-T12 rate table (decode MoE kernel)

Overlay for the b12x W4A16 fused MoE kernel serving Kimi-K3 (QSRT K2
trellis experts, `k2_coupled_h512_h128`). Mounted over the production
image (`kimi-k3-production-issue75-dspark:k3-prefill-sm120-fa4-20260901-r3`)
by `candidates/k3-w4a16-direct-t12-20260902/compose.w4a16-direct-t12.override.yml`.

## What it changes

Trellis weight decode maps each 16-bit window to an E4M3 byte. The served
kernel does this in two steps per weight: a twelve-instruction integer
bijection (`shr, shr, bfi, xor, mad.lo, brev, xor, shr, shr, and, shl, or`)
that ranks the window, then a byte lookup in a 4 KiB modal staircase table
staged in shared memory. On the RTX PRO 6000 (GB202, 188 SMs) the decode
MoE kernel runs one cooperative CTA per SM and is instruction-bound, so the
bijection is most of its time.

With `B12X_SQG_XOR_CHEB_T12_DIRECT_SMEM=1` the kernel instead stages the
64 KiB slice of the precomposed direct table
(`byte(state, bits) = table[((bits - 2) << 16) | state]`,
`b12x._lib.quant.sqg_e4m3.sqg_xor_cheb_t12_direct_lut`) and decodes with a
single `ld.shared.u8` per weight (`packed_decode_trellis_sqg_direct_lut_smem_to_e4m3x8`
in `intrinsics.py`). Both paths yield the same bytes; the fused kernel
output is bit-identical.

Applicability: uniform-rate 2-bit launches on the one-CTA-per-SM grid
whose pipeline leaves 64 KiB under the 101,376 B per-block limit. The
128x128 decode pipeline (route block 8) uses 34,944 B (100,480 B with the
table); route block 16 also fits (35,072 B). The production prefill route
block 48 (68,352 B) and block 32 (51,712 B), and 3/4-bit pipelines, keep
the modal table: the kernel logs one warning per footprint
(`... direct table does not fit ...`) and runs unchanged (block 48 m=1536:
2,510 us either way). Multi-CTA grids, pair-rate kernels and the
mixed-rate kernels (`mixed_trellis.py`) always keep the modal table;
composing a direct-table tier into a mixed launch is refused.

The switch participates in the kernel cache key and in the compile result
(`sqg_xor_cheb_t12_direct_smem`), so a boot can verify that decode launches
actually staged the table.

## Evidence

- Kernel time on production layer weights (layers 1, 50, 92; GPU 0; decode
  m = 1/4/8, batch-8 decode kernel 145 -> 99 us, -32%), output bit-identical
  to the served kernel: `research/decode-step-20260902/out/moe_bench_direct.log`;
  route block 16 at m = 256/1536: 1,941 -> 1,296 / 4,263 -> 2,918 us,
  bit-identical (`out/moe_bench_prefill_block16*.log`); route blocks 48/32
  unchanged (`out/moe_bench_prefill_block48_32.log`).
- `tests/moe/test_w4a16_direct_table_smem.py` (9 tests: bitwise equality
  eager and under CUDA-graph capture, cache-key participation, 3/4-bit
  fallback with a single warning, multi-CTA grid skip, mixed-rate
  composition guard).
- Full W4A16 test regression served vs overlay:
  `research/decode-step-20260902/out/w4a16_regression_{served,overlay}.log`.

Projected production effect: MoE share of the decode step ~23 ms -> ~16 ms
(single stream), i.e. roughly 11-13% more decode tokens/s. Takes effect on
the next boot only.

Status: deployed 2026-09-02 20:40 KST (`candidates/k3-decode-20260902`); the decode grid stages the table, the 48-row prefill block logs the expected fallback.
